# 문서 목차

## 첫 작업 계획

- [ ] [프로젝트 개요](product/overview.md)에 사용자, 문제, 첫 출시 범위를 적습니다.
- [ ] [작업 지침](../AGENTS.md)에 확인된 실행·검증 명령을 적습니다.
- [ ] 구현 소스를 수정하기 전에 [기능 명세 양식](features/_template.md)으로 첫 기능의 합의된 동작과 인수 조건을 파일에 적고 [프로젝트 문서 목록](#프로젝트-문서)에 연결합니다.
- [ ] 첫 기능에 등장하는 용어를 [용어집](domain/glossary.md)에 추가합니다.
- [ ] 모듈 경계와 데이터 흐름이 정해지면 [아키텍처 개요](architecture/overview.md)를 갱신합니다. 설계 결정의 근거는 [ADR 양식](adr/_template.md)에 기록합니다.

양식은 같은 디렉터리에 다른 이름으로 복사합니다. 기능 명세에는 실제 기능 이름을, ADR에는 순번과 결정 제목을 써서 `0001-choose-storage.md`처럼 이름을 붙입니다.

여러 모듈에 걸친 제약은 아키텍처 문서에, 제약이나 설계를 선택한 이유는 ADR에 적습니다. 구현 위치나 검증 근거가 필요하면 관련 코드와 테스트를 링크합니다. 정책이나 제약이 바뀌면 해당 문서를 갱신해 현재 동작을 찾을 수 있게 합니다.

공개 API나 이벤트 계약을 문서화할 때는 `docs/contracts/`를 추가할 수 있습니다. 반복해서 안내하는 개발 절차가 생기면 `docs/guides/`에 정리합니다.

## 기능 명세 작성

- 새 기능은 `초안`으로 작성합니다. 기존 명세를 바꿀 때는 `적용 중`인 본문에 현재 동작을 두고, 같은 파일의 `## 변경 초안`에 예정 동작과 인수 조건을 적습니다.
- 구현과 관련 검증을 마치면 확인한 동작과 인수 조건을 본문에 옮기고 `적용 중`으로 표시합니다. 본문에 반영한 변경 초안은 정리합니다.
- 검증할 시나리오마다 사전 상태, 행동, 관찰할 기대 결과를 적습니다. 명세에는 해당 기능의 실제 시나리오를 넣습니다.

예약 취소 기능의 인수 조건 예시입니다.

- **사전 상태** 확정 예약의 취소 마감 시각은 15시이고 현재 시각은 14시 59분입니다.
- **행동** 예약한 사용자가 취소를 요청합니다.
- **기대 결과** 예약 상태가 `취소됨`으로 바뀝니다.

## 프로젝트 문서

작성한 명세, ADR, 런북 등은 여기에 링크합니다. 분류별 목차를 운영하는 경우 여기에서 그 목차에 연결합니다.
